<Aside title="In short">
Auto mode lets the model edit the project, run commands, and delegate without asking, and it
still asks before the network. It can only be entered when a sandbox works on this machine, and
every command runs inside that sandbox. No one reads tool output before the model does, and
nothing screens it: the trust gate that once did was removed. Two things hold auto mode up, the
mode table and the sandbox, and each is a setting.
</Aside>

## What auto mode decides

Every tool carries a policy class. With no rule written for a call, the mode decides by class.
This is the auto row of the mode table next to the two modes on either side of it:

| Class | `accept-edits` | `auto` | `bypass` |
|---|---|---|---|
| `read` | allow | allow | allow |
| `write` | inside the project, else ask | inside the project, else ask | allow |
| `execute` | ask | inside the sandbox, else ask | allow |
| `network` | ask | ask | allow |
| `delegate` | ask | allow | allow |
| `state` | allow | allow | allow |
| no class | as `execute` | as `execute` | allow |

Source: <Receipt path="src/core/permissions/modes.ts" symbol="MODE_DEFAULTS" />.

Two of these cells are conditions rather than answers. `inside` allows a write when every path in
the call resolves under the project root, and asks otherwise. `sandboxed` allows a command when the
session has a sandbox, and asks otherwise. The engine turns each into an allow or an ask with a
reason the transcript records, such as "auto mode allows commands inside the sandbox".

Source: <Receipt path="src/core/permissions/engine.ts" symbol="modeDefault" />.

Rules still win. A `deny` in `permissions.deny` refuses a call in auto mode as in any other, an
`ask` rule asks, and a tool marked `alwaysAsks` asks every time. The mode is only the default for
calls no rule reaches.

## Entering auto mode

A session enters auto mode in one of three ways, and all three pass the same check:

- `permissions.mode: "auto"` in `.jamcli/config.json`, which sets the mode a session starts in.
- `--permission-mode auto` on the command line.
- `/mode auto` in the interface, which calls `setPermissionMode` on the runtime.

The check is that a sandbox exists. Without one the switch is refused with the reason "auto mode
runs commands without asking only inside a sandbox, and no sandbox is available here", and a
session that asked for auto mode in a file starts in default mode and says so in a notice.

Source: <Receipt path="src/core/permissions/modes.ts" symbol="modeRefusal" />,
<Receipt path="src/core/runtime/index.ts" symbol="setPermissionMode" />.

Switching modes rebuilds the tool set, the system prompt, and the agent, so what the model is
offered changes on the next turn, not the next session.

## The sandbox

The sandbox is detected once per session: bubblewrap on Linux, Seatbelt on macOS, and none
anywhere else. Detection probes that the tool can actually start, because a container without
namespaces has `bwrap` installed and cannot use it. The reason for the outcome is kept and shown
in the status line as `no sandbox` when there is none.

Source: <Receipt path="src/core/sandbox/detect.ts" symbol="detectSandbox" />.

Inside the sandbox a command gets:

- Read access to the filesystem, except a list of credential paths that are hidden: `~/.ssh`,
  `~/.aws`, `~/.kube`, `~/.netrc`, `~/.npmrc`, the Docker and 1Password sockets, and more.
- Write access to the project root, the temporary directory, and nothing else.
- No network, and on macOS no Unix sockets either, since one reaches the Docker daemon as easily
  as a port.
- An environment with credential-looking variables removed.

Source: <Receipt path="src/core/sandbox/seatbelt.ts" symbol="seatbeltProfile" />,
<Receipt path="src/core/sandbox/bwrap.ts" symbol="bwrapSandbox" />,
<Receipt path="src/core/sandbox/paths.ts" symbol="DEFAULT_HIDDEN" />.

Every one of these is a setting under `sandbox` in configuration:

| Setting | Default | Effect |
|---|---|---|
| `enabled` | on where a sandbox works | `false` turns it off, which also makes auto mode unavailable. |
| `network` | off | Lets sandboxed commands reach the network. |
| `writable` | none | Directories besides the project and temp that commands may write. |
| `hidden` | none | Paths hidden in addition to the defaults. |
| `env` | `scrubbed` | `scrubbed` drops credential-looking variables; `minimal` passes only what a shell needs. |
| `env_passthrough` | none | Variables passed by name even when they look like credentials. |

Source: <Receipt path="src/core/config/schema.ts" symbol="SandboxSettingsSchema" />.

## Tool output

In every other mode a person sees a tool's output in the transcript before the model acts on it.
In auto mode the model acts first, and nothing screens what it reads. The trust gate that once
screened tool output in auto mode was removed on 2026-09-29: it was a relevance filter standing in
for an injection defense, and it was never measured as one. What an injection in a file or a page
can make the model do is bounded by the mode table and the sandbox: commands run without network,
writes stay in the project, and every tool that reaches the network still asks.

The `trust` settings are still accepted, so an existing file loads, and read by nothing. A session
whose configuration sets `trust.model` says once that the gate is gone.

Source: <Receipt path="src/core/runtime/index.ts" symbol="createRuntime" />,
<Receipt path="src/core/config/schema.ts" symbol="trust" />.

## What is worth testing

**Sandbox gaps a project needs.** A build that writes outside the project, needs the network, or
reads a credential the sandbox hides fails inside auto mode with a note that names the sandbox.
`writable`, `network`, and `env_passthrough` open each gap on purpose, and the wider each is
opened the less auto mode protects.
